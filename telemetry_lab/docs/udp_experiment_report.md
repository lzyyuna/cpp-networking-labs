# TelemetryLab：基于 C++17 的跨平台 UDP 通信性能实验报告

**项目名称：** TelemetryLab  
**实验时间：** 2026 年 10 月  
**实验平台：** Linux / Windows  
**实验状态：** 当前阶段已收束，网络故障根因保留为未定位

---

## 1. 实验背景与目的

本项目基于 C++17 开发跨平台 UDP 遥测通信程序，支持 Linux 和 Windows 系统之间的数据报发送、接收及性能统计。

本阶段主要研究：

1. 验证 Linux 与 Windows 之间的跨设备 UDP 通信能力。
2. 测试不同发送速率下的报文接收情况。
3. 通过序列号检测报文缺失、重复和乱序。
4. 对比本机通信与真实校园网络通信的性能差异。
5. 初步分析高频 UDP 通信中出现报文缺失的可能原因。
6. 比较追赶式与重置式发送调度，验证发送微突发假设。

实验重点在于学习网络编程、操作系统网络接口及网络性能测试方法，而非验证 UDP 协议本身的可靠性。

## 2. 实验环境

### 2.1 硬件和系统环境

| 项目 | 配置 |
|---|---|
| 发送端 | 学校 Linux 服务器，Ubuntu |
| 接收端 | Windows 个人电脑 |
| 编程语言 | C++17 |
| 构建工具 | CMake |
| 网络协议 | UDP / IPv4 |
| 接收端口 | 9000 |
| 网络环境 | 校园网络，发送端位于虚拟化网络环境 |
| 测试方式 | 跨设备通信、本机 Loopback 通信 |

实验期间 Windows 使用的 IPv4 地址为 `10.29.213.237`。

此前的简单收发验证中，Windows 观察到来自 `10.160.17.102` 的 UDP 报文，说明学校服务器流量经过了不同于容器内部地址的出口路径，存在网络地址转换的迹象。

### 2.2 程序结构

Linux Sender 负责按照指定速率发送 UDP 数据报。

Windows Receiver 采用 Winsock 和生产者—消费者线程模型，使用 BoundedQueue 在接收线程和处理线程之间传递数据。

主要使用的技术包括：

- Winsock / POSIX Socket
- `sendto()` / `recvfrom()`
- RAII 资源管理
- C++ 多线程
- BoundedQueue
- CMake 跨平台构建
- 序列号统计和数据分析

通信报文采用文本格式：

```text
sequence,value
```

例如：

```text
1,10
2,20
3,30
```

序列号从 1 开始递增，接收端通过比较序列号识别数据报缺失及乱序。

## 3. 实验设计

### 3.1 发送速率测试

使用不同发送速率和持续时间进行 UDP 通信测试。

发送端命令示例：

```bash
./build-linux/telemetry_udp_sender 10.29.213.237 9000 10000 10000 catchup
```

表示向 Windows 接收端发送数据，目标速率为 10000 packets/s、持续 10 秒，并采用追赶式调度。最后一个参数也可以设为 `reset`，表示明显落后时重新安排下一次发送。

### 3.2 序列号统计方法

接收端增加以下指标：

| 指标 | 含义 |
|---|---|
| Valid packets | 成功解析的数据报数量 |
| Unique sequences | 不重复的有效序列号数量 |
| Missing | 已观察序列号范围内的缺失数量 |
| Duplicate | 重复出现的序列号数量 |
| Out-of-order | 相对于此前最高序列号发生逆序的报文数量 |

需要注意，Missing 根据序列号 1 至最大已接收序列号进行计算，无法独立识别最大序列号之后的尾部缺失。

因此，完整的报文交付率需要结合发送端实际发送数量判断。

## 4. 实验结果

### 4.1 跨设备 UDP 通信测试

| 目标速率（packets/s） | 持续时间 | 参考发送量 | 有效接收量 | 数量差 | 数量差比例 |
|---|---:|---:|---:|---:|---:|
| 100 | 5 s | 500 | 500 | 0 | 0% |
| 1000 | 5 s | 5000 | 4999 | 1 | 0.020% |
| 5000 | 5 s | 25000 | 24998 | 2 | 0.008% |
| 10000 | 5 s | 50000 | 49959 | 41 | 0.082% |
| 10000 | 10 s | 100000 | 99985 | 15 | 0.015% |

**说明：**

100、1000 和 5000 packets/s 的参考发送量有对应 Linux Sender 输出支持。10000 packets/s 两组的参考发送量根据实验目标与接收端最大序列号整理，尚缺少对应的完整 Sender Summary 复核。

较早的测试尚未全部具备完整序列号统计，因此表中的“数量差”不应一律直接解释为已经确认的网络丢包。

结果显示，在当前实验规模下，大部分报文能够被正常接收，但在较高发送速率下出现少量数据报缺失。

### 4.2 10000 packets/s 重复实验

为观察相同发送条件下的数据波动，在目标发送速率 10000 packets/s、持续 10 秒的条件下进行了三轮复测。

三轮接收端最大序列号均为 100000。

| 指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---:|---:|---:|
| 有效接收 | 99985 | 92653 | 99976 |
| 唯一序列号 | 99985 | 92653 | 99976 |
| 缺失序列号 | 15 | 7347 | 24 |
| 区间缺失比例 | 0.015% | 7.347% | 0.024% |
| 重复报文 | 0 | 0 | 0 |
| 乱序事件 | 3 | 1 | 1 |
| 最大序列号 | 100000 | 100000 | 100000 |

可以观察到：

**第 1 轮和第 3 轮：** 缺失数量较少，分别为 15 和 24 条。

**第 2 轮：** 缺失数量达到 7347 条，明显高于其余两轮，属于本阶段最突出的异常结果。

这些数据说明，即使在相同的目标发送速率下，UDP 数据报的接收情况也可能出现显著波动。

### 4.3 异常轮次的进一步分析

第二轮接收日志出现：

```text
Received: seq=51014
Received: seq=59339
```

由于接收程序每收到 1000 条有效数据才打印一次，两次采样之间虽然接收了约 1000 条有效报文，但序列号跨度达到 8325。

在这一段中，约有 7325 个序列号没有被接收端观察到。

这说明该次异常并非均匀分布的少量缺失，而是存在明显的集中缺失现象。

其可能原因包括：

1. 校园网络转发或 Wi-Fi 链路短时异常。
2. NAT 或中间网络设备出现队列溢出或流量丢弃。
3. Linux 发送端调度不稳定，产生瞬时突发流量。
4. Windows 接收线程短暂停顿，导致 Socket 接收缓冲区溢出。

目前尚未进行双端网络抓包，因此无法确定这些报文具体在哪一环节丢失。

### 4.4 Windows 本机 Loopback 对照实验

为初步验证 Windows Receiver 的处理能力，使用 Windows Sender 和 Windows Receiver 在本机进行 UDP 通信。

发送目标为本机回环地址 `127.0.0.1`，不经过校园网络。

实验结果：

| 指标 | 测试结果 |
|---|---:|
| 目标发送速率 | 10000 packets/s |
| 持续时间 | 约 10 秒 |
| 实际发送量 | 99902 |
| 实际发送速率 | 9987.88 packets/s |
| 有效接收量 | 99902 |
| 缺失序列号 | 0 |
| 重复报文 | 0 |
| 乱序事件 | 0 |
| 交付率 | 100% |

实验中，发送端实际发出 99902 条数据报，而接收端成功收到全部 99902 条。

需要强调，目标数量与实际发送数量之间的 98 条差异属于发送端速率控制结果，不能算作网络丢包。

该实验说明，Windows Receiver 在本机回环网络条件下，能够完成约 10000 packets/s 的数据处理且没有观察到报文缺失。

但是，本机测试与跨设备测试的发送端操作系统和网络路径不同，因此这一结果不能完全排除 Windows 接收缓冲区在跨设备通信时发生瞬时溢出的可能。

### 4.5 catchup/reset 调度策略对照实验

为验证“发送线程落后后连续追赶可能形成微突发，并进一步造成集中缺失”的假设，在 10000 packets/s、持续 10 秒的条件下，按照 `catchup → reset` 的顺序完成三组配对实验。

`catchup` 保持原始发送时间表，落后时允许连续追赶；`reset` 在至少落后一个目标发送间隔时，从本次发送完成时间重新安排下一次发送。

| 组 | 策略 | 发送 | 接收 | 丢失 | 丢失率 | 调度失期 | 最大迟到（us） | 最长追赶 | `<25 us` 间隔 | 乱序 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | catchup | 100000 | 99982 | 18 | 0.018% | 4 | 124.856 | 4 | 1 | 0 |
| 1 | reset | 99995 | 99979 | 16 | 0.016% | 3 | 132.560 | 0 | 3 | 0 |
| 2 | catchup | 100000 | 99984 | 16 | 0.016% | 72 | 3876.582 | 45 | 66 | 5 |
| 2 | reset | 99985 | 99965 | 20 | 0.020% | 8 | 451.168 | 0 | 15 | 0 |
| 3 | catchup | 100000 | 99990 | 10 | 0.010% | 2 | 112.542 | 3 | 0 | 0 |
| 3 | reset | 99990 | 99973 | 17 | 0.017% | 3 | 640.208 | 0 | 0 | 0 |

汇总结果：

| 策略 | 总发送 | 总接收 | 总丢失 | 汇总丢失率 |
|---|---:|---:|---:|---:|
| catchup | 300000 | 299956 | 44 | 0.01467% |
| reset | 299970 | 299917 | 53 | 0.01767% |

第二组 `catchup` 出现了 3876.582 us 最大调度迟到、45 次最长连续追赶和 66 个小于 25 us 的相邻发送间隔，说明追赶式调度确实可能产生用户态发送微突发。

但是，该轮丢失 16 条，少于配对的 `reset` 轮次 20 条；三组汇总中 `reset` 也没有表现出更低的丢失率。因此，本实验验证了微突发的存在，但没有获得“微突发是当前 UDP 丢失主因”的稳定证据。

第二组 `catchup` 同时出现 5 次乱序，属于值得保留的观察现象，但单轮结果不足以建立因果关系。三组实验已经能够回答当前假设，项目不再通过增加重复轮次继续追查。

## 5. 实验结果分析

### 5.1 通信性能评价

从已有结果来看，TelemetryLab 已能够实现每秒上万条小型 UDP 数据报的跨设备传输与接收。

Linux Sender 在已提供的发送日志中表现出较准确的平均速率控制能力，例如：

```text
Target rate: 5000 packets/s
Sent packets: 25000
Elapsed time: 5.00006 s
Actual send rate: 4999.94 packets/s
```

但平均发送速率准确并不代表瞬时发送间隔始终均匀。

另外，本项目目前主要传输短文本报文，尚未测试大负载 UDP 数据报，因此上述结果主要反映高频小报文通信能力，而不是网络最大带宽。

### 5.2 跨设备通信不稳定性的分析

跨设备测试存在少量甚至突发性报文缺失，而本机测试没有观察到缺失。

这使得网络路径相关因素成为值得关注的候选原因。

但两种测试环境不仅网络路径不同，发送端操作系统、线程调度和数据到达模式也不同，因而不能仅凭本机与跨设备实验的差异判定校园网络存在故障。

现阶段可以确认：

- 跨设备通信存在应用层可观察的数据报缺失。
- 在相同目标速率下，缺失数量可能显著波动。
- 某次异常轮次存在集中缺失现象。
- 接收端具备一定的高频小报文处理能力。

尚不能确认：

- 报文是否确实在校园网络中被丢弃。
- 是否存在 Windows Socket 接收缓冲区溢出。
- Linux Sender 的微突发是否是当前报文缺失或乱序的主要原因。
- NAT 或其他中间网络设备是否参与了报文丢弃。

### 5.3 时延测量的限制

当前程序输出的 `mean`、`p50`、`p95`、`p99` 是遥测数值 `value` 的统计结果，并非网络时延。

本阶段尚未实现 RTT、端到端单向时延、抖动或 AoI 的测量。

因此不能根据现有统计数据评价网络延迟性能。

本阶段已完成以下功能：

1. 基于 C++17 的 Windows/Linux UDP Sender 和 Receiver。
2. 基于 CMake 的跨平台项目构建。
3. RAII 网络资源管理。
4. 基于多线程和 BoundedQueue 的接收处理架构。
5. 可配置目标发送速率和持续时间。

7. Windows 本机及 Linux–Windows 跨设备通信验证。
8. 多档发送速率和多轮重复性能实验。
9. catchup/reset 两种发送调度策略及调度迟到、连续追赶、发送间隔分布统计。
10. 三组 10000 packets/s 配对对照实验及可复用 CSV 结果归档。

上述功能已经构成一个可独立运行的 UDP 遥测通信测试原型。

## 8. 阶段性结论

本实验基于 C++17 成功实现了 Linux 与 Windows 之间的跨设备 UDP 遥测通信，并通过多档发送速率和重复实验，初步分析了高频 UDP 数据传输的可靠性。

实验表明：

1. 当前系统具备约 10000 packets/s 级别的小型 UDP 数据报收发能力。
2. Windows 本机 Loopback 实验实现了 99902 条发送、99902 条接收，没有观察到数据报缺失。
3. Linux–Windows 跨设备通信中存在少量报文缺失及个别乱序现象。
4. 一次重复实验中观察到 7347 条序列号缺失，表明通信过程可能存在短时严重异常。
5. 目前尚无足够证据判断异常主要由校园网络、NAT、发送端调度或接收端缓冲机制中的哪一因素引起。
6. catchup 策略在异常调度时可形成连续追赶和微突发，但 reset 策略在三组对照中没有稳定降低丢失率，因而不能将微突发认定为当前丢失主因。

**总体结论：TelemetryLab 已完成跨平台 UDP 通信和初步网络可靠性测量的阶段性目标，形成了可运行的 C++ 网络通信原型和真实环境测试记录。**

项目后续可以继续围绕网络故障定位、时延测量、实验自动化，以及机器人实时遥测通信场景进行扩展。
